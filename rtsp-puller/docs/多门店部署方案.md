# 多门店部署改造方案

> 场景：每个门店在本地部署，由 WorkBuddy 在现场执行安装与初始化。
> 目标：换一家店只需提供 5 个信息，其余全部自动化；核心拉流逻辑零改动。
> 状态：配置隔离部分**待确认**（尚未动代码）；账密验收部分**已落地**（见 §3.4，命令为 `--accept`）

---

## 一、需求定位

门店数从 1 家变成 N 家后，变化的只有"连接参数"（IP / 账号 / 密码 / 门店名 / 时段），
**不变的是**已经真机验证过的核心逻辑：

| 已稳定的部分 | 是否需要改 |
|---|---|
| RTSP Digest 认证（nonce 绑定连接） | 不改 |
| 回放地址格式 `cam/playback?...` | 不改 |
| 归档案命名规则（门店名_通道名_时间_时间_device.mp4） | 不改 |
| 留存删除的安全边界（只删合规文件 + realpath 校验） | 不改 |
| 中断续传、时段跳过、可播放性校验 | 不改 |

所以这次改造的本质是**配置隔离 + 部署流程标准化**，不是功能重写。

---

## 二、现状的三个隔离缺口

| # | 缺口 | 位置 | 影响 | 严重度 |
|---|---|---|---|---|
| 1 | 运行基准目录写死为脚本目录 | `nvr_puller.py:67`<br>`base_dir = os.path.dirname(os.path.abspath(__file__))` | `state/state.json`（进度游标）、`state/index.jsonl`、`state/device.json`（设备名缓存）、`logs/` 全部**全局共用**。同一台机器跑第二家店，进度游标会被覆盖 → 重复拉取或漏拉 | 高 |
| 2 | 只有唯一一份 `config.json` | 项目根 | 无法并存多家店的配置；换店要手改原文件，改错即丢配置 | 中 |
| 3 | 密码明文写在同一份配置里 | `config.json` | 配置文件一旦外发给别人、或贴进聊天/工单，密码即泄露 | 中 |

> 说明：归档文件本身不会混淆（文件名前缀带门店名），但**运行数据会串**，这是必须先解决的。

## 三、改造方案

### 3.1 改造后的目录结构

```
rtsp-puller/
├── nvr_puller.py
├── config.json                    # 保留为模板/默认配置（不含真实密码）
├── configs/                       # 每店一份配置
│   ├── 测试门店A.json
│   └── <门店名>.json
├── secrets/                       # 密码单独存放（与配置分离）
│   └── 测试门店A.pwd
├── data/                          # 运行数据，每店独立
│   └── 测试门店A/
│       ├── state/state.json       # 断点游标
│       ├── state/index.jsonl      # 分段索引（后续上传 Notion 用）
│       ├── state/device.json      # 设备名缓存
│       └── logs/
├── bin/ffmpeg.exe                 # 已自带
└── setup_store.py                 # 新增：一键初始化向导
```

归档目录名 = **`<录像机名称>门店监控视频归档`**（已落地，见 §3.7）：

```
<最大剩余空间磁盘>/<录像机名称>门店监控视频归档/<日期>/<门店名>_<通道名>_<起>_<止>_device.mp4

例：<本机用户目录>\Desktop\测试门店A门店监控视频归档\2026-09-14\
      测试门店A_IPC_20260914145500_20260914152500_device.mp4
```

目录名与归档文件名**同源**（都取录像机的 `General.MachineName`），一台机器一家店时
天然相互区分，"按门店再分一层"的需求由目录命名本身解决。

### 3.2 配置结构变化

新增 `store` 段，`nvr` 段新增密码来源字段，`runtime` 段新增 `data_dir`：

```json
{
  "store": {
    "id": "测试门店A",
    "mode": "store"
  },
  "nvr": {
    "host": "192.168.2.10",
    "username": "admin",
    "password": "",
    "password_file": "secrets/测试门店A.pwd",
    "password_env": ""
  },
  "archive": {
    "root_dir": "auto",
    "organize_by_store": true
  },
  "runtime": {
    "data_dir": "auto"
  }
}
```

**密码取值优先级**：`password` > `password_file` > `password_env`。
三者都为空时直接报错退出（明确提示），而不是拿空密码去连、留下含糊的 401。

**`data_dir: "auto"` 的含义**：解析为 `data/<store.id>/`，`state_file`、`log_dir`、
`device_cache_file` 的相对路径都基于它。这样同一台机器跑多家店天然隔离。

### 3.3 命令行变化（全部向后兼容）

| 新参数 | 作用 |
|---|---|
| `--store <id>` | 等价于 `--config configs/<id>.json`，日常用这个 |
| `--stores` | 列出本机已配置的所有门店及各自进度 |
| `--init` | 交互式初始化向导（见 3.4） |

**不带任何新参数时行为完全不变**（仍读根目录 `config.json`），现有用法和脚本零破坏。

### 3.4 一键验收（**已落地**）与一键初始化（待定）

**3.4.1 账密验收 `--accept`（已实现）**

```bat
python nvr_puller.py --accept
```

三道门禁：① 能登录（HTTP Digest）② 能回放（RTSP Digest `DESCRIBE`）③ 拉得到（实拉 30 秒 + 解码校验）。
另有「部署前核对」输出录像机时钟偏差与通道清单。

结论与退出码：

| 结论 | 允许部署 | 退出码 |
|---|---|---|
| 通过 | 是 | 0 |
| 有条件通过（有告警） | 是，先处理告警 | 0 |
| 待复验（有门禁没验成） | 否 | 3 |
| 不通过（有门禁失败） | 否 | 2 |

实现位置：`nvrcore/acceptance.py`（判定规则）+ `nvrcore/deviceinfo.py:probe_login`（登录探测）
+ `nvrcore/downloader.py:describe_playback`（带分类的回放探测）+ `tools/acceptance_test.py`（101 项离线断言）。

**3.4.2 初始化向导 `--init`（方案待确认）**

```
python nvr_puller.py --init
```

交互顺序：

1. 问 5 个信息：门店名、录像机 IP、账号、密码、拉取时段（默认 09:30-22:30）
2. 生成 `configs/<门店名>.json` 与 `secrets/<门店名>.pwd`
3. 自动跑 `--accept`，等待验收结论
4. 打印结果表，逐项标注通过/失败
5. 询问是否注册开机自启（调用改造后的 `install_startup.ps1 -Store <id>`）

WorkBuddy 在现场部署时，只需把这 5 个信息喂给它，其余由它跑完。

  目录命名 36 + 按日 104 + 单实例锁 37 + 容量测算 50 = **555 项**

### 3.7 归档目录命名（**已落地**）

目录名 = `<录像机名称>门店监控视频归档`，与归档文件名同源：

```json
"archive": {
  "folder_name": "auto",              // auto = <门店名> + folder_suffix
  "folder_suffix": "门店监控视频归档"
}
```

* 换一家门店，**目录名自动跟着变**，不需要手工改配置
* 想固定目录名（不随门店变）就填具体值，或直接用绝对路径 `root_dir`
* 已存在的旧目录**不会被自动搬走**，启动时会告警提示，用迁移工具显式处理：

```bat
python tools/move_archive_folder.py           :: 预览（默认不动文件）
python tools/move_archive_folder.py --apply   :: 执行：只移动，不删除，并同步索引
```

* 顺带修掉一个会污染台账的隐患：`state/index.jsonl` 原先写死在 `state/` 目录，
  自定义了 `runtime.state_file` 的实例（多门店并行、测试场景）会把条目写进别人的索引。
  现已改为**与 `state_file` 同目录**，天生隔离。

## 四、每店部署 SOP（7 步）

| 步骤 | 操作 | 责任人 |
|---|---|---|
| 1 | 复制整个 `rtsp-puller` 目录到门店机器（含 `bin/ffmpeg.exe`） | 实施 |
| 2 | 向门店取得 5 个信息：门店名、录像机 IP、账号、密码、拉取时段 | 实施 |
| 3 | 把账密填进 `config.json`，执行 **`python nvr_puller.py --accept`** 做账密验收：能登录 / 能回放 / 拉得到，附带通道核对与时钟核对。**结论为「通过」或「有条件通过」才继续** | WorkBuddy |
| 4 | 执行 `python nvr_puller.py --init`，按提示录入（含上一步确认的通道号），等待自检全绿 | WorkBuddy |
| 5 | **补历史**：`python nvr_puller.py --day 2026-09-10` 逐日往回补（默认 6 路并发，约 2.2 小时/天），或临时常驻跑 `run_forever.bat` 追平 | WorkBuddy |
| 6 | **配置每日归档**：注册计划任务，每天 09:30 执行 `run_daily.bat`（即 `--day yesterday`），夜里继续把当天量拉完 | WorkBuddy |
| 7 | 次日检查 `--status` 与归档目录，确认首日录像完整（归档目录应为 `<录像机名称>门店监控视频归档`，名字不对说明设备名没读对） | 实施 |

> **调度不要求"准点"，只要求"每天都跑到"。** 具体几点触发由实施方定，脚本这边
> 与触发时刻无关（目标日固定是"昨天"，00:10 跑和 23:30 跑拉到的都是同一天同一个窗口），
> 而且自带两层兜底：
> * **自动补漏**——游标落后于目标日时（漏跑、半途中断）会逐日补齐中间缺的日子，
>   不会只拉目标日就把前面的永久丢掉；回溯上限 `runtime.catchup_max_days`（默认 7 天），
>   超出的区间告警而不静默略过；
> * **单实例锁**——发现已有实例在跑就退出码 `4` 直接跳过，不会两个任务对着同一台
>   录像机同时拉（`run_daily.bat` 已把 `4` 单列为"跳过"，不记成失败）。
> 因此即使把触发频率调得比单批耗时更密（比如每小时一次），也只是空跑，不会出事。

> 第 6 步是日常运行的主形态。**必须算清时间账**：该系列设备回放是 1 倍速推流、
> 无法快进（实测 ≈0.97 倍速），营业时段 13 小时素材单路需约 **13.4 小时**。
> 所以默认**开 6 路并发**（`runtime.parallel_streams`），把这一天压到 **约 2.2 小时**；
> 且 `--day` 模式**不限制运行时段**（夜里继续拉）。若把并发关成 1 路、又只在营业时段内跑，
> 会刚好打平甚至逐日积压。详见 `README.md` §5.6。
>
> 第 3 步是硬门槛。`--accept` 的退出码：`0` = 通过/有条件通过，`2` = 不通过，`3` = 待复验。
> 只有 `0` 才允许进入第 4 步；`2`/`3` 时它会把「卡在哪一道门禁 + 门店需要开什么权限」直接打出来。

> 通道号也由第 3 步覆盖：门店录像机常常满配 16 路、实际只接 1~2 路，其余通道仍留着历史
> 通道名，看起来像全接了。若 `nvr.channel` 配到了没有摄像头的通道，
> 脚本会一直拿到空录像或超时，而且不报错——`--accept` 会在「部署前核对」里直接告警。

### 4.1 多摄像头门店：第 4 步之前先算容量账（**新增，务必执行**）

门店摄像头数量一多（常见 8~16 路），第 4~6 步的做法**必须重新算一遍**，
因为三本账都会变，而且三本都是硬约束：

```powershell
python tools\capacity_plan.py --channels 15          # 按实际摄像头数
```

工具会算出素材总量、存储缺口、每通道可分流数、单批耗时、带宽占用与规模对照表，
资源不够时退出码为 `1`（可直接用于部署脚本判定）。**先把下面三条钉死再动手**：

**① 并发额度是整机共享的，不是每通道各有一份。**
本机型（DH-NVR4216-HDS2）阶梯法实测：**整机同时在传的会话上限 15 路**
（6 路运行中 + 9 路叠加全部正常，保持无掉线；第 16 路拿不到流）。
所以 `parallel_streams` 的有效值是 `min(config 设置, 15 ÷ 通道数)`：

| 通道数 | 每通道可分流 | 有效并发 | 13 小时时段下全店单批耗时 |
|---|---|---|---|
| 1 | 6 | 6 | 约 2.2 小时 |
| 4 | 3 | 12 | 约 4.3 小时 |
| 8 | 1 | 8 | 约 13 小时 |
| **15** | **1** | **15** | **约 13 小时（等于一个营业日）** |
| 20 | 1 | 15（超出排队） | 约 17.3 小时 |

> 15 路门店**没有"多开几条流提速"的空间**了——通道数已把额度吃满；
> 单批约 13 小时仍能落在 24 小时内（余量约 46%），但前提是 15 路并发能连续撑满 13 小时。

**② 存储会先卡住。** 实测码率 153 kbps、13 小时时段：

| 通道数 | 每日素材 | 全店每日 | 留存 7 天 |
|---|---|---|---|
| 1 | 13 小时 | 0.83 GB | 5.8 GB |
| 8 | 104 小时 | 6.7 GB | 47 GB |
| **15** | **195 小时** | **12.5 GB** | **88 GB** |

若把码率提到 2~4 Mbps（为 AI 稽核提画质），15 路每日素材约 **90~175 GB**，
留存 7 天 **0.6~1.2 TB**。**先扩盘，再提画质**，顺序不能反。

**③ 当前脚本实例只归档一个通道。** `nvr.channel` 是单值，多路需要按通道各跑一个
实例（各自独立的 `config.json`、`state_file`、`log_dir`），且各实例
`parallel_streams` 之和不要超过整机 15 路。多通道模式尚未内置。

**④ 部署前必须在现场实测三件事**（本工具用的是本机型实测值，不能照搬）：

1. **该设备真实并发上限** —— 阶梯法逐条加回放会话，每条确认"已在出数据"后再加下一条，
   直到拿不到流。注意**认证握手层不设限**（26 条 `DESCRIBE` 都通过），限制发生在传流时；
2. **并发能否连续撑满整个时段** —— 实测只验证了保持 15 秒不掉线，长跑稳定性未知；
3. **实时预览是否与回放共用会话池** —— 未验证；若共用，营业时段可用额度会更少。

## 六、风险与注意事项

| 风险 | 说明 | 应对 |
|---|---|---|
| **门店账号缺"回放"权限** | 大华账号权限分项勾选。只有"实时预览"权限的账号，回放地址返回 403，拉不到任何录像 | 现场跑 `--accept`：门禁 2 会直接判定「账号没有『远程回放』权限」；要求门店建**专用只读账号** |
| **通道号配到了没接摄像头的通道** | 设备满配 16 路但实际只接 1~2 路，其余通道仍保留历史名称，看着像全接了。配错通道会一直拿到空录像且不报错 | `--accept` 的「部署前核对」会告警并给出可用的通道号 |
| 录像机时间与门店机器时间不一致 | 回放地址用的是**设备本地时间**。设备偏慢时脚本会向『还没录到』的未来要录像 → 探测 404 → 游标直接跳过 → 该段永久漏掉 | `--accept` 自动核对两边时钟，偏差 >120 秒即告警并给出 `safety_lag_seconds` 兜底值；根治办法是两边对到同一 NTP 源 |
| 跨店复制时带出密码文件 | `secrets/` 会随目录一起被拷走 | 复制部署包前先清空 `secrets/` 与 `configs/`，或把这两个目录加入排除清单 |
| 用 admin 账号长期跑 | 权限过大，一旦泄露影响整台录像机 | 坚持用专用只读账号 |
| **并发把录像机的出流占满** | 默认 6 路并发回放（`runtime.parallel_streams`）。**额度是整机共享的**：阶梯法实测本机型同时在传的会话上限 **15 路**（6+9=15 路全部正常，第 16 路拿不到流；认证握手层不设限）。但门店还要同时看**实时预览**，占满会让预览卡顿或掉线 | 单通道默认 6 路、**稳妥值 8 路**；多通道门店按 `min(设置, 15 ÷ 通道数)` 分配（见 §4.1）。填 `1` 即退回顺序拉取 |
| **多摄像头门店容量失控** | 通道数一多，素材总量、并发额度、存储三本账同时变紧：15 路门店 195 小时素材/天、12.5 GB/天、留存 7 天 88 GB；而整机只有 15 路并发额度，**每路只剩 1 条流，不能再提速** | 第 4 步前先跑 `python tools\capacity_plan.py --channels N`（资源不够退出码 1），按 §4.1 的三条结论先定盘、再提画质 |
| **并发同时发起会集体 401** | 真机实测：同一瞬间开 6 路回放，**6 路首轮全部 `401 Unauthorized`**，要等一个退避周期才恢复 | 已内置错峰启动 `runtime.start_stagger_seconds`（默认 1.5 秒），使各路的发起时刻拉开；实测错峰后 **0 次 401**。除非改坏，否则不要把它设为 0 |
| 出厂默认通道名（如 `IPC`） | 归档文件名不易辨认 | 部署前建议门店在录像机或云联里改成实际位置名，再 `--refresh-device` |
| **改了门店名后旧归档目录被落下** | 归档目录名跟随录像机名称。改了名之后脚本会在新目录重新开始，旧目录里的录像**既不会被留存清理扫到**（可能把盘写满），也**不会进入上传流程** | 启动日志会告警提示；用 `python tools/move_archive_folder.py --apply` 迁移（只移动不删除，并同步 `state/index.jsonl`） |
| **调度漏跑一天，那天就永久丢了** | `--day` 原本是"起点前移到目标日窗口开头"，中间漏掉的日子**再也不会被补，而且不报错**；本地留存只有 7 天，设备侧也可能已覆盖 | **已加固**：改为从游标那天逐日补到目标日，回溯上限 `catchup_max_days`（默认 7 天），超出的区间明确告警。回归覆盖见「按日归档 104 项」 |
| **同一台机器上两个任务同时跑** | 调度器只看"进程退没退出"，看不到"上一批还没跑完"。触发比单批耗时（约 2.2 小时）更密时会出现两个实例：并发翻倍打满录像机、两批写同一文件名互相覆盖、游标互相踩 | **已加固**：内置 `state/puller.lock` 单实例锁，占用时退出码 `4` 跳过；陈旧锁自动接管不会锁死自己。`run_daily.bat` 已把 `4` 单列。回归覆盖见「单实例锁 37 项」 |
